# 上半：iztro 到底改了什么（实测，确定）

## 方法

- 直接调 `iztro.astro.withOptions`，不经本项目包装层；`type:'lunar'` 直接喂农历，隔离时间层。
- 每次调用都显式传全套 `config`（**iztro 的 config 是模块级全局且粘滞**，见下方「API 陷阱」）。
- 种子随机 300–400 盘 / 1930–2019 / `timeIndex` 0–12 / 双性别；**十天干全覆盖**，
  「年支阴阳 × 性别」四格全覆盖（阴年男 111 / 阳年女 98 / 阴年女 97 / 阳年男 94）。
- 六个组合全跑：`{default, zhongzhou} × {heaven, earth, human}`，按「路径 → 差异桶」聚合，
  再按星名聚合成 加/减/移位 三类。
- 運限面另跑 200 盘 × 随机目标日期，覆盖 大限/小限/流年/流月/流日/流时。

脚本：`/private/tmp/.../scratchpad/zz-{diff,stars,horo,dup,body}.mjs`（临时件，未入库；
结论已固化在本文档与 `tests/zhongzhou-snapshot.test.ts`）。

## 结论 A：两个开关完全正交

`algorithm` 的差异在 `heaven/earth/human` 三种 `astroType` 下**逐字节相同**；
`astroType` 的差异在 `default/zhongzhou` 两种 `algorithm` 下**逐字节相同**。

> **这与本项目自己的文案不符。** `src/mcp/server.ts:166` 与 `src/schemas/input.ts:212` 都说
> `astroType`「only meaningful with algorithm: "zhongzhou"」。实测：`astroType` 在
> `algorithm:'default'` 下**照样生效**，效果一模一样。iztro 自己的类型注释也把 `astroType`
> 标为「中州派特有」，但代码里 `withOptions` 的 `switch (astroType)` 根本不看 `algorithm`
> （`node_modules/iztro/lib/astro/astro.js:367`）。**这是文案缺陷，不是行为缺陷。**

## 结论 B：`algorithm:'zhongzhou'` 的完整差异（穷举，仅此 5 条）

| # | 变化 | 条件 | 频率 |
|---|---|---|---|
| B1 | 杂曜 **删** 截路、空亡 | 恒定 | 400/400 |
| B2 | 杂曜 **增** 截空 | 恒定 | 400/400 |
| B3 | 杂曜 **增** 劫杀、大耗、龙德 | 恒定 | 各 400/400 |
| B4 | 天伤 / 天使 **互换** | 仅「阴男阳女」 | 209/400（阳年女 + 阴年男） |
| B5 | 岁前十二神第 7 位 **大耗 → 岁破** | 恒定 | 400/400，本命盘与流年盘同步 |
| B6 | 命主（`soul`）改由 **年支** 取，而非命宫支 | 年支 ≠ 命宫支 时 | 266/300 |

**除此之外一个字都没动。** 明确实测为「无差异」的面：

- **四化：十天干全覆盖，禄权科忌四星一颗未变**（含争议最大的庚干）。
- 十四正曜位置与亮度、天府系、紫微系 —— 无变化。
- 全部辅星（左辅右弼、文昌文曲、禄存擎羊陀罗、天魁天钺、火星铃星、地空地劫、天马、红鸾天喜）—— 无变化。
- 五行局、命宫/身宫、宫干（五虎遁）、十二宫名、大限起始年龄、博士十二神、将前十二神 —— 无变化。
- 運限面（`horoscope()`）：**唯一差异是 B5 传导到 `yearly.yearlyDecStar.suiqian12`。**
  运四化、运曜（运禄羊陀魁钺昌曲马鸾喜）、大限/小限/流月/流日/流时 —— 全部无变化。

### B3 的两颗是纯重复星

| 新增星 | 位置 | 与既有字段的关系 |
|---|---|---|
| 龙德（杂曜） | 与岁前十二神的「龙德」**同宫** | 300/300 完全重复 |
| 劫杀（杂曜） | 与将前十二神的「劫煞」**同宫** | 300/300 完全重复（只差「杀/煞」用字） |
| 大耗（杂曜） | 年支对宫再阳顺阴逆移一位 | 与岁破宫位 **0/300** 重合，是真正的新位置 |

即：开了 `zhongzhou` 之后，同一颗神煞会在输出里**出现两次**（一次在 `suiqian12`/`jiangqian12` 字段，
一次在 `adjectiveStars` 数组）。下游 LLM 若按「杂曜列表」计数会重复计入。

### B2 的规则

`截空` 不是新星，而是「截路 / 空亡」二选一：生年支阳则取截路那一宫，阴则取空亡那一宫。
实测 300/300 满足「截空所在宫的地支阴阳 == 生年支阴阳」。

### B4 的规则

天伤恒在仆役、天使恒在疾厄（= `default` 行为）；**阴男阳女则二者对调**。
实测 300/300 完全符合。

## 结论 C：`astroType` 的完整差异

`earth`（地盘）：把天盘的 **身宫**当命宫重排；`human`（人盘）：把天盘的 **福德宫**当命宫重排。
两者都以该宫**干支纳音**重取五行局。

**重排的**（`node_modules/iztro/lib/astro/astro.js:272` `rearrangeAstrolable`）：

- 命宫位置、十二宫名旋转
- 五行局（由新命宫干支纳音定）
- 十四正曜全部重排（亮度、四化标记随星走）
- 长生十二神（宫气）、大限 `decadal`（range/干/支）、`ages`、`isBodyPalace`
- 天才、天伤、天使

**不重排的**：

- 全部辅星与其余全部杂曜
- 宫干、博士十二神、将前十二神、岁前十二神、小限 `ages` 起宫
- 生年四化

> 这一半其实**正确**：除紫微系/天府系外，安星几乎全部锚在绝对地支（左辅右弼按生月、
> 昌曲空劫按生时、禄存羊陀魁钺按年干、火铃马鸾喜按年支），与哪一宫是命宫无关，
> 不重排本来就不会错位。

**運限面**：只有 `decadal.*`（index / 干支 / 宫名 / 运四化 / 运曜）随之改变；
流年、流月、流日、流时、小限**完全不变**（它们本来就锚在地支，不依赖命宫）。

## 结论 D：`astroType` 下的三处内部不自洽（实测）

| # | 现象 | 频率 |
|---|---|---|
| D1 | 顶层 `earthlyBranchOfBodyPalace` 不更新，与 `isBodyPalace` 标记的宫**对不上** | 366/400 |
| D2 | 天寿留在天盘位置。iztro 自己的公式是 `身宫 + 年支`（`location.js:613`），而身宫已移动 —— **但注意下半第 12 行**：唯一找到的三盘来源列举重排项时只提天才、不提天寿，所以这一条可能是「照文献办」而非缺陷。存疑，不要当 bug 修 | 366/400 |
| D3 | 命主 / 身主（`soul` / `body`）不重算。在 `algorithm:'default'` 下命主本应随新命宫支走 | 318/400 |

D3 有个反讽的副作用：**`zhongzhou` + `earth/human` 反而自洽**（B6 让命主改由年支取，
而年支不随重排变），**`default` + `earth/human` 才是坏的**。而本项目的默认值正是
`algorithm:'default'` + `astroType` 可自由选 —— 用户选 `earth` 而不选 `zhongzhou` 时，
拿到的是一张命主自相矛盾的盘。

## 结论 E：一个 API 陷阱（本项目已正确处理，记录备查）

`chart.horoscope()` **在调用时刻读取 iztro 的全局 config**，而不是绑定建盘时的 config。
先批量建六张盘、再批量取 horoscope，六张盘会全部拿到最后一次 `withOptions` 的 algorithm。
本项目 `src/core/chart.ts` 的 `resetIztroConfig()` 在每次 `.horoscope()` 前后都调用，已经堵死这条路。
（这条是写对拍脚本时踩到的，不是 src 的缺陷。）

# 下半：与中州派文献比对（网络资料，逐条定级）

**定级口径**（照抄任务要求）：

- **Confirmed** —— 多个独立可信来源一致，且 iztro 与之相符。
- **Contradicted** —— 可信来源在规则上一致，而 iztro 做的是别的。
- **Unsourced** —— iztro 改了某处，但找不到任何来源描述它。
- **Undetermined** —— 来源互相矛盾，或根本找不到来源。

外加一档，因为「Confirmed 要求多源」这条我自己也得守：

- **Supported（单一来源）** —— 只找到**一个**来源，iztro 与之相符。**不等于 Confirmed。**

## 最重要的一条

**第 1、3 行是本次最高价值的发现，也是最容易伤到用户的一条：**

用户设 `algorithm:'zhongzhou'`，**得到的四化仍然是通行版的四化**。
而四化恰恰是中州派与通行版分歧最大、也最影响断盘结论的地方 —— 一颗化科从太阴挪到天府，
整张盘的吉凶走向就变了。用户会以为自己拿到了中州派盘，实际拿到的是「通行版四化 + 换了几颗杂曜」。

这不是 iztro 的偷懒：`config.mutagens` 是**开放**的，用户本可以自己传一份中州派四化表。
但 `algorithm:'zhongzhou'` 这个名字**主动制造了它并不兑现的承诺**。

## 一句话说清楚「真正的验证需要什么」

上面每一个 Confirmed 都只是「与网络二手描述一致」。要把它升级成真正的验证，需要：

1. **王亭之的纸本原著**（《中州派紫微斗数初级讲义》《深造讲义》《紫微斗数讲义》），
   逐条抄出安星诀与四化表，像 `tests/ziwei-rules.ts` 对通行版那样**独立实现一份中州派安星诀**，
   再与 iztro 对拍数千盘。
2. 一个**中州派自己的排盘工具**做外部对拍（本项目 §8.4 对通行版做过 ziwei.pub 对拍）。
3. 对三盘用法（第 14 行）还需要判断这本身是不是一个「排盘」问题 —— 若三盘是**定盘**手段
   （靠出生分钟选一张），那它压根不该是一个用户可自选的枚举参数。

在这三件事任何一件做成之前，**「中州派已验证」这句话不能说**。
